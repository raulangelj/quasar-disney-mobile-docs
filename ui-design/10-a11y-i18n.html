11 · The screen-reader model

choose

This is the one part not already implied by earlier decisions, and it is where carousel apps usually fail. A continue-watching tile is seven views: artwork, play overlay, progress bar, time-remaining, overflow button, title, rating chip, episode line. Left alone, VoiceOver treats each as a separate stop.

How B is built

  onPress={onCardPress}>
  <Artwork … accessibilityElementsHidden importantForAccessibility="no-hide-descendants" />

  accessibilityRole="button"
  accessibilityLabel={t('tile.overflow.a11y', { name })} />

The rule generalizes: one tile = one accessibility element, plus one element per additional action. Decorative artwork is always hidden from the tree. The label is a translated template, not string concatenation — which is why this decision has to be made alongside i18n rather than after it.

SurfaceAnnouncement rule
Tab bar (unlabeled icons)accessibilityLabel per tab + accessibilityState={{selected}}. Inert tabs also get accessibilityHint "Disponible pronto".
Password visibility toggleLabel changes with state (Mostrar / Ocultar contraseña), not just the glyph.
Auth inline erroraccessibilityLiveRegion="assertive" (Android) + AccessibilityInfo.announceForAccessibility (iOS) — otherwise a failed login is silent to a screen-reader user, which is criterion F2 failing for that user.
Progress barFolded into the tile's label as a percentage; not its own element.
Loading gate / skeletonsSkeletons hidden from the tree; the gate announces "Cargando".
No-internet overlayaccessibilityViewIsModal so focus can't wander to the navigator underneath.

Verification, honestly stated: UI tests are deferred to 1b (doc 02), so there is no automated a11y assertion in 1a. The props above are written as the atoms are written — near-free then, a sweep across every component later — and verified by a 10-minute VoiceOver + TalkBack pass added to the Tuesday-AM smoke checklist. That is a real gap, recorded rather than papered over.

12 · Internationalization — the mechanism

choose

DF8 already requires that no string be hardcoded. The open question is what the strings layer is. Note this app genuinely needs interpolation and plurals, not just lookup: “11 min restantes”, “Comenzó hace 7 h 26 min”, and the screen-reader templates above.

OptionMechanismConsequence
A recommended react-i18next + i18next, one es-419 bundle Plurals, interpolation, and namespaces out of the box; the production-standard answer, which matters because this repo is explicitly a migration template for the real app. ~1 hour to wire, and adding en-US later is a JSON file. Cost: two dependencies for a single-locale demo.
B Hand-rolled typed strings module (t('auth.password.title') over a typed key map) ~30 lines, zero dependencies, compile-time key checking that i18next doesn't give you by default. But plurals and relative time become hand-written, and a migration template that ships a bespoke i18n layer teaches the wrong lesson. Reasonable fallback if Saturday slips.
Ci18n-js + expo-localizationRuled out — expo-* packages contradict the bare-RN decision (doc 15).

One thing that needs your call, because it crosses into the API contract. Doc 04 says Container.name is the row header and is “i18n in the client” — but a row name arriving from a feed is data, and the client can only translate it if the wire sends a key rather than a display string. Three ways: (i) the wire sends a key ("home.row.marvel") and the client resolves it — clean, but the backend then owns our key namespace; (ii) the wire sends an already-localized string and the client renders it verbatim — normal for a real content API, and it means row headers are the one text on screen not in our bundle; (iii) Phase-1 mocks send display strings and we note that the real API must send localized text per the request's locale. I'd take (iii) — it matches how content APIs actually behave and defers nothing incorrectly — but it contradicts doc 04's wording, so it belongs in the doc and in 1.11's contract.
