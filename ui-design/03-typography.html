Decision 3 — Typography

Palette is now locked to option A and is identical in every mock below. Spacing, radius, and layout are the same neutral defaults as page 02. The only variable is the typeface — and the type ladder (sizes, line heights, weights, tracking) is deliberately the same numbers in all three options, so you are judging letterforms, not scale.

Inter and Manrope are rendered from real font files fetched into ui-design/fonts/ — not a CSS fallback. If a specimen below looks like the system font, the file failed to load and you should tell me rather than judge it.

Why this decision is bigger than it looks here. The demo is shown with iOS and Android side by side (doc 01, §"Scale & shape"). A system-font stack renders SF Pro on one device and Roboto on the other — different letterforms, different widths, different vertical metrics, in the same screenshot. The Dinsey- wordmark already has this exact bug (doc 02 §10: SVG <text> with an Avenir Next stack that falls back on Android), and it is filed as a defect to fix before sign-off. Choosing a system stack here re-introduces the same class of problem across every screen.

Implementation note that applies to options 2 and 3: in bare React Native, numeric fontWeight is unreliable for bundled fonts on Android — it silently synthesizes or ignores weights. The theme's typography tokens must name files (Inter-Regular / -SemiBold / -Bold / -ExtraBold), not weight numbers, and each is linked via react-native.config.js + npx react-native-asset. That is ~4 files per family, ~350 KB total — irrelevant for a locally-installed demo.

Option 1 — System stack (SF Pro / Roboto)

zero bundle · diverges per platform

-apple-system on iOS, Roboto on Android. Nothing to bundle, nothing to link, native text rendering and native Dynamic Type behavior for free. Tradeoff: the two platforms do not match, and this build's whole argument is visual fidelity demonstrated on both at once. Note the specimen below shows only the iOS half — Roboto isn't installed on this machine, which is itself the point.

Option 2 — Inter (bundled)

recommended identical on both platforms · OFL

Neutral humanist sans built for screen UI. Large x-height and open apertures make the 10–12 pt metadata line — the smallest text in the whole app, and there is a lot of it — hold up better than any of the alternatives. Real tabular figures, so “11 min restantes” doesn't wobble as the number changes. Renders identically on iOS and Android. Tradeoff: deliberately characterless; it will not make the storefront feel like a brand on its own.

Option 3 — Manrope (bundled)

geometric · closest to the wordmark

Semi-geometric sans — rounder bowls, more even stroke, a distinctly "streaming brand" feel. It is the closest freely-licensable proxy for the Avenir Next geometry the Dinsey- wordmark is drawn in, so chrome and brand agree instead of merely coexisting. Also identical on both platforms. Tradeoff: the geometric forms are less legible than Inter at the 10–12 pt sizes the metadata rows live at, and Manrope's default figures are proportional — the time-remaining line shifts slightly as digits change unless we opt into tabular figures.

The type ladder — same in every option above

confirm, don't choose

Seven steps, derived from the sizes measured in the reference transcription rather than from an abstract modular ratio — a 1.25 ratio would have produced a 33 pt h1 and a 17 pt h3, neither of which matches what the reference actually does. Line heights are absolute, because React Native's lineHeight is a number, not a multiplier. Sizes are unitless RN density-independent points.

Notes carried into the doc

No mono family. Nothing in Phase 1 shows code, IDs, or aligned numerics beyond the time-remaining line, which the caption step handles with tabular figures. Adding a mono family would be a token nobody imports.

Tabular figures on caption only — the one place a changing number would otherwise shift the layout on every tick.

Font scaling (iOS Dynamic Type / Android font size) is decision 11's business; the ladder is authored so that the two chrome steps (micro, caption) are the ones that will need maxFontSizeMultiplier caps, not the headings.
