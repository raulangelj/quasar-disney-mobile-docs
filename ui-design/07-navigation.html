Decision 7 — Navigation

Most of the structure is already fixed by earlier docs, so this page separates what is locked from the three things that are genuinely still open. Locked: React Navigation (doc 03, decision 8); a binary navigator split driven by an auth selector in the shell (ADR-0010); a 4-item bottom tab bar with only home live (doc 02); card tap raises a native Alert, not a route (DF7).

Why the split is two navigators and not one stack with a guard. With two root navigators, an unauthenticated user has no route to the storefront — it isn't mounted. A single stack with a redirect guard leaves the screen reachable and relies on the guard being correct everywhere, which is the class of bug that survives into production. It also means the theme mode (light for auth, dark for app) can be chosen at the navigator boundary rather than per screen.

Recommendation

A. Respecting the platform back contract is decision 15 territory, and Android's hardware back is not optional — you handle it or the OS closes your app mid-flow. Since it must exist, iOS's equivalent gesture should behave the same way.

Two rules that come with it: back from PasswordEntry clears the password field but keeps the email (matching the reference's (editar) affordance), and back is blocked during an in-flight submit so a pop can't race the mock's resolve. Both are auth-feature behavior, recorded here because they are navigation contracts.

Choice 3 — headers

choose
OptionApproachConsequence
A recommended headerShown: false everywhere; screens render their own chrome (AppHeader, AuthSheetLayout) The reference has no native header on any screen: the storefront's Para ti is a large in-content title that scrolls, and the auth back button floats over the gradient with no bar behind it. A native header would also style differently per platform — the divergence problem again. Cost: safe-area insets become ours to handle (decision 10).
B React Navigation's native header, restyled with theme tokens Free safe-area handling, free back button, free iOS large-title behavior. But it cannot produce either reference screen without fighting it, and it renders platform-natively, so iOS and Android headers won't match in the side-by-side demo.

With A, the tab bar stays React Navigation's BottomTabBar with a custom tabBar renderer — it keeps safe-area bottom inset and route state handling, while the 4 unlabeled items match the reference. Unlabeled tabs still need accessibilityLabel on every item, since there is no visible text for a screen reader to announce; that is the single most commonly skipped a11y defect in a tab bar (decision 11).
