Decisions 8–9 — Theme support & iconography

Two system-level decisions on one page. They share a root cause: both are places where a reasonable-looking default would quietly break something already decided.

The theme trap. This app has two surface modes, and it is tempting to call them light and dark — at which point the next developer wires them to useColorScheme(), and the auth flow turns dark on a phone in dark mode. That is wrong: the auth sheet is light because MyDisney's sheet is light, not because the device asked. The modes are surface roles, not appearance preferences, and naming them for their role is what stops that bug from ever being written.

8 · Theme structure — two axes

recommended

A theme (the brand's token values) times a surface mode (app or auth). Criterion A1 asks for a second theme that re-skins both modes without touching a component — which only works if the mode axis lives inside the theme rather than beside it. 

// shared/theme/types.ts
type SurfaceMode = 'app' | 'auth';   // role, NOT 'light' | 'dark'

interface Theme {
  name: string;                        // 'qcplus' | 'ember'
  modes: Record<SurfaceMode, ModeTokens>;  // every mode, same shape
  type: TypeScale;                        // mode-independent
  space: SpaceScale;                      // mode-independent
  radius: RadiusScale;                    // mode-independent
  motion: MotionTokens;
}

// The shell provides the theme once; each navigator provides its mode.
<ThemeProvider theme={themes[active]}>        // root — brand axis
  <ModeProvider mode="auth"> …AuthNavigator…  // light sheet, always
  <ModeProvider mode="app">  …AppTabs…        // dark chrome, always
</ThemeProvider>

Consequences worth stating in the doc: useColorScheme() is never called in Phase 1 — a device in light mode sees the identical app. Mode is fixed at the navigator boundary, so it cannot drift out of sync with the route, and no Redux state holds it. And because every mode exposes the same token keys, a component reads colors.text.secondary without knowing which surface it's on — that is what makes A1 mechanical rather than aspirational.

react-native-svg is already a hard dependency, and doc 03 doesn't list it. Every placeholder-art file in architecture/assets/placeholder-art/ is an .svg, and so is every brand wordmark — but React Native cannot render SVG without react-native-svg. Doc 03 §7's hard-dependency list (RN, RTK, React Navigation, Styled Components, axios, redux-persist, encrypted-storage, netinfo) omits it, so as written the assets decided in STEP-1.2 cannot be displayed by the stack decided in STEP-1.3.

Two ways out, and the choice belongs to you: (i) add react-native-svg — one well-maintained library, autolinked, and it makes this icon set free plus renders the wordmarks and art directly; or (ii) export every asset to @1x/@2x/@3x PNG and keep the dependency list as-is, which also happens to resolve the un-outlined-wordmark defect (OQ-13 / doc 02 §10) since PNGs carry no font dependency at all. I lean (i) plus PNG export for the wordmarks only: SVG for art and icons that must scale and re-tint, PNG for the one asset whose text rendering is already a known platform hazard. Either way doc 03 needs updating — that is a real find, not a formality.

A recommended Hand-authored 13-icon set as RN components over react-native-svg, in shared/components/icons/ 13 icons is small enough to author in an hour, and each one accepts color from theme tokens so active/inactive tab states and both surface modes come free.
